# Sim v2 realism review: load -> latency / CPU / memory for an autoscaled Redis-like KV service (2026-10-17, R-20261017-017)

Scope and honesty note. This file adds to, and does not repeat, `paper/notes/load_metrics_literature.md` (LML), which already
holds 40+ graded sources (keys in `paper/refs.bib`). Section A lists the sources opened in this pass; section B condenses the
LML sources that bear on the question; section C is the change list with the calibration that settles each item.
Grades: A = claim read in the source; B = real measurement on another system / vendor / blog; C = my inference.
Tool limit: the fetch tool cannot decode PDFs, so several papers are abstract-only or UNVERIFIED (section D).

## A. New sources opened in this pass

1. **Mansouri, Ullah, Dhingra, Babar, "Design and Implementation of Fragmented Clouds for Evaluation of Distributed Databases", arXiv 2209.09487 (2022)**,
   https://arxiv.org/abs/2209.09487 (key `mansouri2022fragmented`).
   Shows: Redis v6.0.11 cluster on 2/4/8 VMs (2 vCPU, 4 GB each), YCSB A-F, 10K records: "the more nodes are in a cluster, the higher throughput we achieve", but "the throughput of the 8-nodes Redis cluster is at most two times of the throughput for a 2-nodes Redis cluster" (Sec. IV-B3). Grade B (tiny dataset, emulated WAN testbed, client bottleneck not excluded).
   Implies: the only independent open-source Redis Cluster datum I found says scaling is sublinear (4x nodes gave at most 2x) => keep `theta` as a free parameter below 1; theta=1 should not be the default claim. Calibrate theta in stage B (see C3). Do not import 0.5 as a value: the testbed is not ours.

2. **Sivko, "How quickly can the Kubernetes HPA scale your app?", Coroot blog, 2022-04-19**, https://coroot.com/blog/how-quickly-can-the-kubernetes-hpa-scale-your-app/ (key `sivko2022coroot`).
   Shows: on one EKS cluster (HPA target 50 % CPU, 2-3 replicas) 2 min 5 s elapsed from CPU crossing 50 % to scale-out with default settings; 30 s after metrics-server resolution was set to 10 s; author attributes most of it to the 60 s metrics resolution (not the 15 s sync). Grade B (practitioner, n=1 cluster).
   Implies: the reaction delay of the real HPA baseline is not just the 15 s sync period; observation staleness (metrics resolution) belongs in the threshold baseline: add `metric_lag_steps` (about 0-4 steps) and calibrate on our cluster's metrics-server/Prometheus scrape settings. Change.

3. **Zhang, Guo, Tan, Guan, Jiang, "KIS-S: A GPU-Aware Kubernetes Inference Simulator with RL-Based Auto-Scaling", arXiv 2507.07932 (2025)**, https://arxiv.org/abs/2507.07932 (key `zhang2025kiss`).
   Shows: an RL autoscaler (PPO) trained on a simulator/emulator of a K8s inference service and deployed on one node; reports P95 improvements over CPU-HPA baselines; the page shows no quantitative simulator-vs-real validation and gives no latency/queueing equation (Sec. VI, Tables I-III). Grade B (preprint, GPU inference, not KV).
   Implies: precedent that RL-autoscaler papers train in simulation without publishing a fidelity check; our stage B calibration plus a held-out sim-vs-real latency/CPU comparison is a differentiator. No parameter to import.

4. **Calheiros et al., "CloudSim: a toolkit for modeling and simulation of cloud computing environments and evaluation of resource provisioning algorithms", Softw. Pract. Exper. 41(1):23-50 (2011)**, https://doi.org/10.1002/spe.995 (key `calheiros2011cloudsim`).
   Shows: metadata verified via Crossref only; I did not read the abstract or text. Grade C.
   Implies: the standard cloud-simulator citation for "simulation-based evaluation of provisioning"; cite only for that. I make no claim about its queueing or validation methodology (UNVERIFIED).

## B. Sources from LML that carry the argument (full grading in LML; keys in refs.bib)

5. **Li, Sharma, Ports, Gribble, "Tales of the Tail", SoCC 2014**, https://doi.org/10.1145/2670979.2670988 (`li2014tales`). Abstract-level (A): servers show much worse tails than queueing models predict; after removing interference Memcached reaches p99.9 32 us at 80 % utilisation vs 5 ms for a naive deployment. Implies: M/M/1 tail `exp(-mu(1-rho)x)` is an ideal lower-bound shape; add `tail_scale kappa >= 1` and calibrate it. Change + calibrate.
6. **Zhou et al., AHPA, arXiv 2303.03640 (2023)**, https://arxiv.org/abs/2303.03640 (`zhou2023ahpa`). HTML read (B): RT = queueing term + `otherlatency`; M/M/c (Erlang C + Little) better with few pods, M/M/1 better with many. Implies: keep per-pod M/M/1 for many pods, add additive `other_latency_s`; for 1-5 pods test a shared M/M/c variant against measured latency. Keep + add term.
7. **Whitt, "Fluid Models for Multiserver Queues with Abandonments", Oper. Res. 54(1), 2006**, https://doi.org/10.1287/opre.1050.0227 (`whitt2006fluid`). Abstract (A): fluid models are first-order accurate under heavy load; result depends on the abandonment-time distribution but not on service-time shape beyond the mean. Implies: FIFO fluid backlog + 60 s timeout is defensible near/over saturation (asymptotics are for many servers; Sim v2 has 1-30 single-server pods, so cite as motivation only). Keep; calibrate `timeout_s` against the real client.
8. **Redis docs: Diagnosing latency issues**, https://redis.io/docs/latest/operate/oss_and_stack/management/optimization/latency/ (`redisdocs_latency`). Single thread, slow commands delay everyone, network latency ~200 us on 1 Gbit/s TCP, fork stalls (A, documentation). Implies: add `service_cv2` (M/G/1) and `other_latency_s`; optional fork-stall capacity dip independent of load (CPU not proportional to served ops then). Change.
9. **Redis docs: Benchmarks**, https://redis.io/docs/latest/operate/oss_and_stack/management/optimization/benchmarks/ (`redisdocs_benchmark`). Single instance throughput is hardware/client/pipelining dependent; "limited by the network well before ... CPU" in many setups (A). Implies: the measured 101,506 ops/s at c=1 versus mu=1000 means mu cannot be a Redis-intrinsic number; it must be the throughput of the real *client+pod* chain at the SLO. Calibrate mu directly.
10. **Redis docs: Memory optimization**, https://redis.io/docs/latest/operate/oss_and_stack/management/optimization/memory-optimization/ (`redisdocs_memory`) and **Client handling** (`redisdocs_clients`). Memory follows dataset size and does not shrink on delete; client output buffers grow only with slow consumers (A). Implies: confirms "no memory model driven by load" (consistent with removal from observation); if kept, memory = dataset + backlog-proportional buffers, not lambda.
11. **Redis blog, Atomic slot migration (8.4), 2026**, https://redis.io/blog/atomic-slot-migration/ (`redisblog2026asm`). Vendor benchmark (B): legacy migration of ~5 GB took 192-219 s with latency spikes up to 127 ms; ASM took 6.4-8.6 s with <5 % average latency rise. Implies: `rebalance_steps=1`, `delta=0.3` match neither regime; derive duration from data volume, make loss CPU-steal based (C).
12. **K8s docs: HPA**, https://kubernetes.io/docs/concepts/workloads/autoscaling/horizontal-pod-autoscale/ (`k8sdocs_hpa`). Sync 15 s, tolerance 0.1, 300 s downscale stabilisation, 30 s initial-readiness delay, 5 min CPU init period (A). Implies: `control_step_s=15` is correct; threshold baseline needs tolerance, stabilisation, proportional step.
13. **K8s SIG Scalability SLOs**, https://github.com/kubernetes/community/blob/master/sig-scalability/slos/slos.md (`k8sslos`) and **Harter et al., Slacker, FAST 2016** (`harter2016slacker`). Stateless pod start SLO p99 <= 5 s excluding image pull; image pull dominates start time in 2016 Docker (A). Implies: `startup_delay_steps=2` (30 s) is plausible for warm images, but the real delay is a distribution (warm/cold, data load); make it random and calibrate.
14. **Alibaba trace (Luo et al., SoCC 2021)**, https://doi.org/10.1145/3472883.3487003 (`luo2021alibaba`). Abstract (A): microservices are more sensitive to CPU than memory interference. Implies: CPU is the load-coupled observable; memory is decoupled. Keep.
15. **Rocksteady (SOSP 2017)** https://doi.org/10.1145/3132747.3132784 (`kulkarni2017rocksteady`) and **ElastiCache resharding doc** (`awselasticache_resharding`). Cheap live migration is possible in research systems; production resharding is compute-intensive, keep CPU < 80 %/50 % while resharding (A). Implies: migration dip should depend on spare CPU, not be a fixed 30 %.

## C. Recommended model changes and the stage B measurement that settles each

| # | Change | Evidence | Settled by (stage B sweep) |
|---|--------|----------|---------------------------|
| C1 | Calibrate `mu_ops_per_pod` as SLO-feasible throughput of the real client+pod chain (not a docs figure); report it with CI | redisdocs_benchmark; own c=1 run 101,506 ops/s vs 1000 | Open-loop rate sweep at c=1 (and fixed cpu limit 200m): rate vs achieved ops/s, CPU, p50/p95/p99 until saturation |
| C2 | Add `kappa` (tail_scale >= 1), `other_latency_s`, `service_cv2`; keep per-pod M/M/1 as the ideal | li2014tales; zhou2023ahpa; redisdocs_latency | Same sweep: fit p95(rho) against the M/M/1 curve; fit offset at low rho; compare shared-queue M/M/c at c=2..5 |
| C3 | Keep `theta` free; run theta in {1, 0.9, 0.8, lower} as sensitivity, default only after measurement | mansouri2022fragmented (4x nodes -> at most 2x, other testbed) | Sweep c = 1,2,4,8 with load generator scaled to avoid client saturation; max SLO-feasible throughput vs c; log client CPU |
| C4 | `rebalance_steps` from data volume and migration rate; `rebalance_loss` as CPU-steal; legacy-like and ASM-like sensitivities | redisblog2026asm; awselasticache_resharding; kulkarni2017rocksteady | Scale c -> c+1 under 3 loads at the real dataset size; record migration duration, throughput dip, p95 during migration (needs Redis version used by DInos) |
| C5 | Stochastic, state-dependent `startup_delay` (warm vs cold image, data load) | k8sslos; harter2016slacker; redisdocs_replication | 20+ scale-outs: time pod-created -> Ready -> first served request, warm and cold node |
| C6 | Observation lag `metric_lag_steps` and HPA-faithful baseline (tolerance 0.1, 300 s stabilisation, proportional step) | sivko2022coroot; k8sdocs_hpa | Read metrics-server resolution / Prometheus scrape interval; one HPA step-load test measuring crossing -> new pod Ready |
| C7 | CPU model: `cpu = baseline + served/capacity` with optional background term; do not assume linearity above ~80 % | redisdocs_latency (fork); awselasticache_resharding | CPU% vs served ops from the C1 sweep (linearity check at low, mid, high load); run once with persistence on/off if used |
| C8 | Memory: keep out of the observation; if needed, `mem = dataset + buffers(backlog)`; scale-in feasibility bound | redisdocs_memory, redisdocs_clients, awselasticache_resharding | Record used_memory/RSS during C1 sweep at two dataset sizes; slow-consumer test only if backlog buffers matter |
| C9 | Add held-out sim-vs-real check (latency, CPU, pods vs time) for a replayed workload | zhang2025kiss (no such check reported) | Replay one workload on the real cluster for the baseline policy and compare trajectories |
